# 双版本发布计划（A：资产识别融合版 + B：资产识别×拦截代理实验版）

> **状态：已完成**（2026-09-11 双版本交付：`release/v1.0-asset/` 与 `release/v1.0-asset-guard/`，
> 指标与变更见 [changelog](../changelog.md)）。
> 来源：2026-09-11 会话计划（原 `.zcode/plans/`）归档。

> 分工背景：资产与风险识别由你负责，队友做监测系统。
> **版本 A** = 静态资产识别+风险评定的独立版，三层融合接口，作为队友监测系统的"资产/基线供给方"；
> **版本 B** = A 的超集 + MCP 拦截代理 + 逐事件判定 + 阻断 + 评测对比，验证"资产识别×运行时监测"组合效果。
> 版本形态：无 git 仓库，用 `release/` 目录快照 + 工件版本元数据 + CHANGELOG。B 基于 A 增量，不 fork。

## 版本 A：v1.0-asset（约 2 天）

### A1 交付物收敛与契约冻结（0.5 天）
- 所有输出工件加版本元数据 `{version, generated_at, spec}`；补 scan/bom/findings 的工件 Schema（节点/边 schema 已有）。
- `solution/api.py`：库入口 `run_all(root)` / `load_artifacts()` / `judge_events(events)`——把 declared-vs-observed 差分暴露为**事件级判定入口**，这是队友系统最关键的融合点。

### A2 三层融合接口（1 天）
- **L1 工件**：out/*.json 契约文档（字段说明 + 最小示例）；
- **L2 Python 库**：`policy_baseline()` 导出声明包络（工具清单+scope+T 层级+egress 白名单+隐藏工具清单）——队友监测系统可直接当判定基线消费；`judge_events(events)` 供其调用；
- **L3 REST**：复用 server，新增 `/api/baseline`（基线导出）与 `/api/artifacts`（打包下载）；
- 固化 `solution/requirements.txt`（pyyaml/pyjwt/jsonschema/networkx/fastapi/uvicorn）。

### A3 文档与版本快照（0.5 天）
- `release/v1.0-asset/`：代码快照 + `README_集成.md`（三种接入方式各配最小可执行示例）+ CHANGELOG + 指标卡（对账 24/24、包络 12/12、变异 10/10、校验器 0 发现、测试 16/16）。
- 验收：以"队友视角"分别用工件/库/REST 三种方式各跑通一次。

## 版本 B：v1.0-asset-guard（约 3.5~4 天，A 完成后）

### B1 MCP 拦截代理（1~1.5 天）
- `guard/proxy.py`（FastAPI）：8 条 MCP 路由透明转发到真实 server，逐事件记录 JSONL（trace 头/method/工具/参数/结果摘要/延迟）；
- `guard/docker-compose.guard.yml`（override 文件，**不改靶场原文件**）：把 opspilot-app 的 `MCP_*` 指向代理，按需 `docker compose -f ... -f guard override up -d opspilot-app` 启用；
- 验收：B-SUP/B-RD 正常业务经代理零差错（透明性）。

### B2 逐事件判定 + 阻断（1~1.5 天）
- `guard/engine.py`：启动时加载 A 版 `policy_baseline()`；每条 `tools/call` 走加性风险分——违反声明（清单外/隐藏工具）+60、参数越界（`tenant="*"`、跨 scope、`.env` 路径、`curl|sh` 模式）+30~40、按 `X-Trace-Id` 的链路状态机累积（污点乘数）；
- **R≥70 拒绝该次调用**（返回 JSON-RPC error）并记录阻断依据；40~70 告警放行；审计简版 `guard/audit/*.jsonl` per-trace（含 prompt 上下文标记与工具链序列）；
- 硬验收：四个良性模板 + 三个诱饵（sandbox-exec/password-policy-check/threat-intel）**零误伤**。

### B3 组合效果评测（1 天）
- `make replay` 全量 5200 事件过代理 → 四项指标：检出率（80 恶意 ≥95%）、误报率（良性 <5%）、响应时间（<1s）、CPU（<5%）；
- **基线增益对比实验**：同一代理在"仅参数黑名单（无资产基线）"与"加载声明包络"两种模式下跑全量 replay，产出检出/误报差异表——直接量化"资产识别对运行时监测的增益"，答辩核心素材；
- 评测报告落 `out/eval/`。

### B4 版本快照（0.5 天）
- `release/v1.0-asset-guard/`：A 全部内容 + guard + 评测报告 + README（override 启用方式/架构图/指标）。

## 里程碑与风险
- **MA1**（A 完成）：三层接口示例全部可执行，快照交付队友；
- **MB1**：代理透明性（良性零误伤）；**MB2**：replay 指标达标 + 增益对比成文。
- 风险：① override 与队友 compose 版本差异 → 文档锁定 compose v2 语法并给启用命令；② 全量 replay 吞吐 → 事件异步落盘、判定纯内存查表（微秒级，响应指标无忧）；③ 阻断引发 replay 连锁失败 → 属预期检测效果（如 C2-B 在 `debug_exec` 处断链即记一次检出）。

总计约 6 天：A 2 天（先交队友，不阻塞并行融合），B 3.5~4 天。
