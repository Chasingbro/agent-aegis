# 融合与测试计划（我方 solution × 队友 agent-scanner）

> **状态：待评审**（2026-09-14 制定）。依据：两侧源码逐文件事实核查
> （[modules/agent-scanner.md](../modules/agent-scanner.md)、[architecture.md](../architecture.md)）
> + 2026-09-14 官方靶场同靶对跑实测。
> 前置决策：**谁做能力 1 的主干**需要与队友确认（分工问题），本文给出建议与两条可选路径。

## 0. 结论摘要

- 两个项目在赛题**第一部分**上重复投入：都做"资产静态识别 + 风险检测"，资产闭集与风险族高度重叠。
- 能力覆盖不对等：队友只有能力 1（无运行时探测、无阻断）；我们能力 1 + 能力 2 都有可运行实现与评测。
- 单看能力 1 的**可信度**，对方更强：每次运行算四项指标（分母为 0 时 `not_measured` 而非伪造满分）、
  负样本陷阱、留出集防过拟合、规则三层外置与合并语义单测；我们的 24/24、12/12 是手写期望的对账，
  `oracle/score.py` 存在但未接流水线，且无第二环境、无"关掉适配层"开关。
- 单看能力 1 的**深度**，我们更强：14 类节点 / 10 类边闭集 + JSON Schema 校验器 + 声明/观测双面与差分 +
  AgentRiskBOM（T1-T5 / A1-A4 / 6 输入评分 / 控制映射 / 10 项变异差分）+ CVE 版本匹配 + 外网投毒页 + 越权语义。
- **建议路线**：以我们为主干，把对方的三件套（generic/profile 分层与 `--generic-only`、
  bench 评测器与负样本口径、留出集与测试纪律）整建制移植（**方案 A**，约 3~4 天）；
  若分工已定"队友负责静态、我们负责运行时"，则走**方案 B：双引擎工件级融合**（约 3 天）。
- 两条路线都从**阶段 0 差异裁决**开始：同靶对跑的 38 条并集逐条判真伪，这既是融合正确性的地基，
  也是答辩时"双引擎互证"的现成证据。

## 3. 判断：哪边效果更好

- **不能直接比"100% vs 24/24"**：双方基线都是自建口径，分母由各自定义。可比的是**口径可审计性**
  与**过拟合风险**，这两项对方更强（我们唯一接近的对照物 `oracle/ground_truth.yaml` 并未接入运行）。
- 分维度结论：
  - 能力 1（静态识别）：**对方工程成熟度更高**（度量 + 泛化纪律 + 规则外置 + 测试规模）；
    我们胜在覆盖面与证据深度（观测面、BOM、CVE、页面投毒、越权语义）。
  - 能力 2（运行时监控与阻断）：**我们独有且已实证**（cat2 56/56 检出阻断、良性 5120 零误报、判定 0.052 ms）。
  - 整体赛题完成度：**我们更完整**（两个能力都有可运行实现与评测数据）。
- 因此不是二选一，而是"**能力 1 取长补短、能力 2 我们独担**"。

## 4. 融合方案

### 方案 A（推荐）：我们主干 + 移植对方三件套

移植清单（按收益排序）：

- **A1 规则分层与通用层度量**：把我们的规则拆成 generic（跨环境谓词）+ profile（靶场适配），
  引入 `--generic-only`，让"通用算法"单独出成绩；运行时探测器同理 —— 容器名、端口、用户名、
  服务名从代码挪进 profile 数据文件。
- **A2 度量接线**：把 `bench/metrics.py` 的评测器接到我们统一工件（或先给 `oracle/score.py` 接线），
  采用 `not_measured` / 负样本陷阱 / provenance 口径，`cli.py bench` 每次输出四项指标与退出码。
- **A3 留出集**：把 `simulated-target` 作为第二环境纳入回归，脚本化"第二环境扫描"，
  并保留"刻意不断言高分"的诚实口径（差距如实记录，而不是调参抹平）。
- **A4 补共同缺口**：新增 `package` 依赖资产类型（requirements.txt / Dockerfile）；
  MCP 识别补 FastMCP `@mcp.tool()` 装饰器解析（双方当前都不支持，而留出集 `evil-mcp` 正是该形态）。

保留：14 类节点 / 10 类边 + JSON Schema + 校验器 + BOM + 包络 + 观测差分 + guard。
产出：一套工件、一个度量入口、两个环境（官方靶场 + 留出集）。成本约 3~4 天。
代价：需与队友确认"我方主干"；移植对方代码须在作品报告中标注分工与来源。

### 方案 B：双引擎工件级融合（若分工已定"队友静态、我们动态"）

- 编排：新增 `fusion/` 层，同时调用两套引擎（各自解释器/venv），产出统一工件。
- 映射：13 类资产 ↔ 14 类节点、9 ↔ 10 类边、6 风险类别 ↔ 我们的规则族；
  ID 命名空间需要映射表（如对方 `script:skills-pdf-export-scripts-export-py` ↔ 我方 `skill:pdf-export` 的脚本）。
- 去重合并：按 `(target, category, canonical_evidence.file:line)` 去重，双方证据并入 `provenance[]`。
- 统一元数据：编排器统一写 `_meta`（含 `schema_version` 与两个引擎版本），顺带修掉"5/6 工件无 `_meta`"。
- 运行时增强：guard 的 baseline 可吸收扫描器发现（隐藏工具 → `hidden_tools_forbidden`，
  宽权限工具 → `wildcard_capable_tools`，敏感路径 → `sensitive_paths`，外联 sink → `egress_allowlist`），
  形成"静态声明 → 运行时判定"的闭环。
- 成本约 3 天；长期风险：两套规则并行维护、口径漂移（用"单侧规则改动必须过联合 bench"作门禁）。

### 方案 C（不推荐）：换成对方为主干

会丢掉 BOM / 包络 / 校验器 / 观测差分 / 变异差分与既有交付版本；且对方通用层仍含靶场字面量，
等于把已交付的深度换成尚未证明的通用性。

## 5. 测试计划

### 阶段 0：差异裁决（0.5 天）

- 环境：`bench` 只要 `--target` 指向靶场即可（本机已实测通过）；对方的集成测试
  `tests/test_integration_range.py` 按自身仓库相对路径找靶场，故需在 `reference/agent-scanner/` 下
  建 junction `AgentRange-player` → 根目录靶场；运行用 `PYTHONDONTWRITEBYTECODE=1` + 系统 Python，
  无需安装依赖。
- 动作：双引擎同靶对跑（首轮已完成，见 §1）；把两侧并集（约 38 条）逐条人工裁决。
- 产出：差异裁决表（归属：双方共识 / 我方独有 / 对方独有 / 超范围 / 误报），作为本文档附录。
- 验收：不存在"双方都漏"的 ground truth；每条"仅一边报"都有归属结论。

### 阶段 1：统一工件与映射器（1.5 天；方案 B 必做，方案 A 可选）

- 单测：类型/边/类别映射全覆盖、无悬空边、ID 映射幂等、**去重前后 GT 命中数不变**、
  证据合并保留双来源、统一 `_meta` 后 schema 校验零违规。
- 验收：同一批发现于 JSON / REST / 前端三处一致；全部工件带 `_meta`。

### 阶段 2：泛化合流与静态驱动运行时（1.5 天）

- 规则分层迁移 + `--generic-only` 度量；第二环境回归；
  变异测试（改容器名/服务名/目录名、加良性诱饵、移动恶意件）要求指标不退化。
- baseline 增强后 guard 复测：cat2 56/56 检出阻断、良性 5120 零误报不退化（作为回归门禁）。

### 阶段 3：统一评测与门禁（1 天）

- 一键脚本 `cli.py bench`（或 `make fused-bench`）串起：扫两环境 → 四项指标 → 阈值比对 → 退出码。
- 门禁表落地（见 §6）；CPU <5% 整改（ASGI 直通 / 旁路镜像 / 仅在 force 时走反代）。

## 7. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 双方口径不可比（都是自建基线） | 结论易被质疑 | 差异裁决表 + 双引擎互证；文档明确标注"自建基线非官方答案" |
| 2 | 对方通用层仍含靶场字面量 | 移植后污染我们的通用层 | 迁移时一律进 profile；沿用并扩充其字面量黑名单测试 |
| 3 | 双方都不支持 FastMCP 装饰器 | 通用 MCP 生态漏检 | 补装饰器 AST 解析；用留出集 `evil-mcp` 做回归 |
| 4 | ID / 类别映射歧义 | 去重错误、漏报被掩盖 | 映射表单测 + "去重前后 GT 命中数不变"断言 |
| 5 | 规则双份维护 | 口径漂移 | 优先方案 A；走 B 则设联合 bench 门禁 |
| 6 | 版权与原创性 | 参赛作品原创性声明 | 作品中写明分工、来源与授权；保留双方 CHANGELOG |
| 7 | 我们缺 `package` 资产类型 | 依赖清点漏报 | 移植对方的 packages 识别 |
| 8 | `_meta` 契约未兑现 | 融合接口不可信 | 编排器统一写 `_meta` + 契约测试 |

## 8. 明确不做

- 不把对方在 `attack/` 攻击脚本上的危险能力判定纳入主清单（攻击方工具不是被保护资产）——归"扩展发现"。
- 不做双主干长期并行（方案 A 落地后，对方规则以 profile/规则文件形式存在，不再独立运行）。
- 不修改 `release/` 冻结快照与官方靶场源码。
